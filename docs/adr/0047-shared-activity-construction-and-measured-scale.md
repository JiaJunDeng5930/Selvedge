# 0047: Derive activity surfaces from their user relationships

Date: 2026-10-14

Status: Accepted

## Context

The previous activity construction retained observations, selected-parent
dependencies, admission and complete project drafts. Its projection nevertheless
treated a necessary fact as a separate summary, exposed every dependent field,
and selected surface width from an activity category. Proofs of that projection
could establish its equations while the resulting interface obscured the work.

Treating each menu as a separate layout problem would leave the same loss of
meaning at the next activity. Adding a presentation enum without a consumer would
not change that boundary either.

## Decision and reasons

Retain the existing activity and relation owners, and make the common projection
consume their requested view, completion boundary and per-subject expression
witnesses. Necessary information can be expressed by a checked candidate, its
owned parameter or the actual effect observation; an unexpressed subject keeps
an inline fallback. The identity of an original project and an editable draft
remains distinct even when their displayed names initially agree. This lets the
construction avoid repetition without using string equality as a substitute for
meaning.

Use the same reading and interaction grammar for the activity rows and whole
navigation. Decoration and independent actions have different spatial demands;
the navigation column and principal activity must share the available space.
Their actual content measurement determines preferred sizes within common
reading limits, instead of allocating a fixed width by the menu's name.

Measure the actual primary and supporting fonts through the existing font cache.
The body font's reference advance cannot stand in for a different role's font.
Keeping these observations in the existing request/accept protocol avoids a
second cache or an unobserved sizing approximation.

Specialize the fixed physical limit after a capacity-parametric font request
constructor has supplied its plan and correspondence evidence. This keeps role
measurements bound to the complete request protocol without forcing the checker
to normalize the large closed bound in the runtime's calibration proof.

Separate an unfinished parameter buffer from an applied configuration. Preserve
the existing command semantics and correlate asynchronous completion with the
requesting view instance, so a result can complete the domain operation without
closing a newer view. Fresh draft occurrences also prevent a discarded project's
old completion from attaching to a reopened draft.

## Assurance boundary

Executable obligations belong with the owning production operations. Integration
checks exercise native input and completion boundaries. Physical measurement and
page inspection assess the actual layout and task, independently of successful
rendering or proof checking. None of these constructions claims to prove that a
person has understood a fact.
