# Remote control through Cloudflare

Selvedge can connect its existing service to a Cloudflare Workers relay backed by
Durable Objects. Both ends initiate HTTPS/WebSocket connections on TCP 443. The
host keeps its local web interface, CLI, journal and task execution. No inbound
port, VPS, public host IP or purchased domain is needed. A Cloudflare account and
a deployed relay are required. This change does not include a phone interface.

The executable authorization and receipt model starts at
[remote feature](../theories/Features/Remote.v), with its grants, permissions,
generations and receipts declared in [feature state](../theories/Features/Domain.v).
[Remote proofs](../theories/Features/RemoteProofs.v) bind the complete access and
request outcomes to the actual operations, including permission replacement,
receipt authority and generation monotonicity.
[Entry proofs](../theories/Features/RemoteEntryProofs.v) connect an admitted
control request to the real task executor. Administration stays local; replacing
or revoking a grant clears that controller's receipts, and a generation is never
reused. This domain owns authorization and retained results; task execution and
transport authentication belong to their respective boundaries.

The shared wire definitions and
endpoint rules live in [remote/protocol.mjs](../remote/protocol.mjs); the deployment
package is [relay](../relay/README.md). TLS terminates at Cloudflare, so Cloudflare
can see relayed messages. This is not end-to-end encryption.

## Deploy the relay

Use Bun 1.4.2 or later, Node 22 or later and an authenticated Wrangler installation:

```bash
bun install --frozen-lockfile
cd relay
bun x --no-install wrangler login
bun x --no-install wrangler secret put RELAY_ENROLLMENT_TOKEN
bun run deploy
```

Enter a fresh random enrollment secret when Wrangler prompts, for example one
generated by `openssl rand -base64 32`. Do not put it in `wrangler.jsonc` or in
source control. Deployment prints an HTTPS origin such as
`https://selvedge-remote-relay.YOUR-SUBDOMAIN.workers.dev`. Check the Cloudflare
account's Durable Objects availability and usage limits before relying on it.

The relay's enrollment credential only registers installations; it does not
replace their host credentials. The host identity is saved privately under its
service home. Keep that directory separate from writable project roots and
include it in private backups.

## Connect a local Selvedge service

Run these commands from the Selvedge checkout. Replace the URL with the deployed
Worker origin and use the same `--home` value as your local server:

```bash
read -rs -p 'Relay enrollment secret: ' SELVEDGE_RELAY_ENROLLMENT_TOKEN
export SELVEDGE_RELAY_ENROLLMENT_TOKEN
bun host/cli.mjs --home /absolute/path/to/service-home remote init \
  --relay-url https://selvedge-remote-relay.YOUR-SUBDOMAIN.workers.dev
unset SELVEDGE_RELAY_ENROLLMENT_TOKEN
```

`remote init` registers the installation and updates only the `remote` setting in
the selected current-format `config.json`. The enrollment credential is accepted
from the environment, never a command argument. Host credentials are stored in
`remote-identity.json` with private file permissions; neither status nor pairing
responses contain them. The configuration contains only a nonsecret reference:

```json
{
  "remote": {
    "relay_url": "https://selvedge-remote-relay.YOUR-SUBDOMAIN.workers.dev"
  }
}
```

Restart the local server to load the new setting, then enable remote access:

```bash
bun host/cli.mjs --home /absolute/path/to/service-home remote enable
bun host/cli.mjs --home /absolute/path/to/service-home remote status
```

The existing `server` command starts the service. Reuse its usual configuration
and workspace; do not start a second server against the same service home. An
absent or `false` `remote` setting leaves the connector unconfigured.

## Pair and manage a controller

Create a pairing code on the host:

```bash
bun host/cli.mjs --home /absolute/path/to/service-home remote pair
```

Give the returned host ID, relay URL and short-lived code to the controller's
pairing flow. The controller creates and retains its own random token and uses
the shared relay protocol. Inspect the request locally and approve the displayed
device identity with explicit permissions:

```bash
bun host/cli.mjs --home /absolute/path/to/service-home remote pending
bun host/cli.mjs --home /absolute/path/to/service-home remote approve \
  --request-id REQUEST_ID \
  --permissions '{"read":true,"control":true,"configure":false,"approve":false}'
```

The permission object always contains the four Boolean fields shown above. Use
`read` for snapshots and subscriptions, `control` for task interactions,
`configure` for task settings and `approve` for human tool approvals. All
permission admission and command classification are defined by the native
feature and harness assembly; local service administration stays on the host.

Managed Git worktrees use the same native lifecycle as local tasks.
`create_worktree_task` and `create_workspace_task` require both `control` and
`configure`; `list_worktrees`
and `read_worktree` require `read`, and `retry_worktree_archive` requires
`control`. Keep the service home outside the source Git repository so private
service state is excluded from checkout copies. Worktree creation and archiving
run after their journal commit; inspect the worktree status for their eventual
physical result. A live task sharing a checkout prevents its owner from archiving
that checkout.

Review grants with `remote status`, revoke a device with its controller ID, or
disable access for the environment:

```bash
bun host/cli.mjs --home /absolute/path/to/service-home remote revoke \
  --controller-id CONTROLLER_ID
bun host/cli.mjs --home /absolute/path/to/service-home remote disable
```

The local management routes use the existing loopback host, authorization and
origin boundary. They are not forwarded by the relay. Opening the local web
interface still establishes a local browser session; exposing that interface
through a reverse proxy is unnecessary for this feature.

## Controller integration and validation

A future controller uses the pairing endpoint, obtains a short-lived one-use
WebSocket ticket, then speaks the shared `command`, `snapshot`, `subscribe` and
`unsubscribe` protocol. Retain a command's `request_id` when retrying after a
lost response. The native receipt is committed with the command decision;
WebSocket delivery alone is not a commit acknowledgment. Protocol constants and
frame definitions in [RemoteProtocol.v](../theories/Host/RemoteProtocol.v) are
authoritative; [protocol.mjs](../remote/protocol.mjs) invokes their extracted decoder.

The [focused regression suite](../tests/README.md) exercises the actual
WebSocket transport, service journal and local Cloudflare Worker runtime. The
loopback HTTP/WebSocket mode exists only for explicit test setup; production
configuration requires an HTTPS origin on port 443.

Run the repository's ordinary proof/build checks and remote integration tests:

```bash
bun run check
bun run test
```

These local checks do not deploy resources or validate a particular Cloudflare
account's availability, billing or live TLS routing.
